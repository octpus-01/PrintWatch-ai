# 服务端系统与边缘推理平台联调报告

**版本**：v1.0
**日期**：2026-08-19
**作者**：PrintWatch AI 项目组
**适用范围**：本文档记录服务端系统（`src/RLserver`）的重新设计与实现过程，以及其与树莓派边缘推理平台（Raspberry Pi）之间的端云通信联调全过程，可作为学术论文的工程实现章节素材。

---

## 1. 项目背景与研究目标

### 1.1 研究背景

3D 打印（FDM 熔融沉积成型）过程中，翘曲（Warping）、层移（Layer Shift）、挤出异常（Extrusion Issues）、拉丝（Stringing）及"意面怪"（Spaghetti）等缺陷具有突发性与不可逆性，若不能及时发现将导致材料与时间的浪费。传统人工巡检效率低、主观性强，难以满足实时质量控制需求。

本项目构建"边缘端推理 → 数据上报 → 服务端重训 → 模型下发"的端云协同主动学习闭环：边缘端（树莓派）承担轻量级实时推理，服务端承担数据汇聚、模型重训与模型版本发布，通过 HTTP 接口实现两者的数据同步与模型更新。

### 1.2 研究目标

本阶段工作聚焦于服务端系统的重新设计，使其能够与边缘推理平台按照既定接口规范（`doc/API_INTEGRATION_GUIDE.md`）进行协同，具体目标为：

1. 实现服务端与边缘端的标准化 HTTP 数据同步与模型下发接口；
2. 建立可靠的边缘数据存储、汇聚与模型版本管理机制；
3. 提供可扩展的重训（Retrain）扩展点，支持后续主动学习算法的接入；
4. 在真实局域网环境中完成端云联调，验证系统闭环的完整性与稳定性。

## 2. 系统总体架构

### 2.1 端云协同闭环

系统采用"训练-部署-监控"分离的三层架构，端云之间的数据流与控制流如下：

```
┌──────────────┐  ① POST /api/v1/sync_data（高置信度推理数据）   ┌──────────────┐
│  边缘端(树莓派) │ ────────────────────────────────────────────▶ │    服务端     │
│  推理 + 数据采集 │                                                │ 存储/重训/发布  │
│              │  ② GET /api/v1/get_latest_model（拉取新模型）     │              │
│              │ ◀────────────────────────────────────────────── │              │
└──────────────┘                                                 └──────────────┘
```

交互时序（与接口规范一致）：

1. 边缘端每 5 秒推理一次，每 4 次（约 20 秒）筛选置信度 ≥ 0.5 的帧，存入本地 SQLite；
2. 边缘端每 10 分钟（`SYNC_INTERVAL`）将未同步数据批量 `POST /api/v1/sync_data`，成功后标记为已同步；
3. 边缘端每 30 分钟（`MODEL_CHECK_INTERVAL`）`GET /api/v1/get_latest_model`，有新版则自动热更新；
4. 新模型加载成功后，边缘端清理本地 7 天前的历史数据，为新模型重训保留近一周数据。

### 2.2 技术选型

| 层次 | 选型 | 说明 |
| :--- | :--- | :--- |
| 服务端框架 | Flask 3.1 + Waitress | 轻量 WSGI 框架，生产级 WSGI 服务器 |
| 服务端存储 | SQLite（Python 标准库 sqlite3） | 单文件数据库，零额外依赖 |
| 鉴权方式 | HTTP Header `Authorization: Bearer <token>` | 常量时间比较（hmac.compare_digest）防时序攻击 |
| 边缘端推理 | ONNX Runtime（CPU） | ResNet-18 分类模型，输入 32×32 CIFAR-10 格式 |
| 边缘端框架 | Flask + requests | 提供实时监控 Web 界面与数据上报客户端 |
| 训练后端 | PyTorch + timm（GhostNet 等） | 服务端重训扩展点预留 |

## 3. 服务端系统设计（`src/RLserver`）

服务端系统按照"单一职责、可插拔扩展"原则重新设计，由以下模块构成：

### 3.1 模块结构

| 模块 | 文件 | 职责 |
| :--- | :--- | :--- |
| 配置管理 | `config.py` | 通过环境变量读取服务配置（端口、Token、数据目录、批量上限等），并给出合理默认值 |
| 鉴权模块 | `auth.py` | Bearer Token 校验，采用 `hmac.compare_digest` 常量时间比较，鉴权失败返回 401 |
| 数据存储 | `database.py` | SQLite 建表与操作封装：推理记录表、模型版本表、设备表；支持线程安全的事务访问 |
| 模型仓库 | `models_store.py` | 模型版本管理：版本号递增、模型注册、最新模型查询 |
| 重训扩展点 | `retrain.py` | 重训"插槽"（Socket）：后台线程调度 `run_retraining()`，防止并发重训；用户在此实现自有训练逻辑 |
| API 路由 | `api.py` | Flask 应用工厂，实现两个核心接口及健康检查、错误码映射 |
| 入口 | `main.py` | CLI 入口：启动服务（`python -m src.RLserver.main`）或手动触发重训（`--retrain`） |

### 3.2 数据库设计

```sql
CREATE TABLE records (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id TEXT NOT NULL,          -- 设备唯一标识
    timestamp TEXT NOT NULL,          -- ISO-8601 时间戳（UTC）
    label TEXT NOT NULL,              -- 预测标签
    confidence REAL NOT NULL,         -- 置信度（0~1）
    image_path TEXT NOT NULL,         -- 解码后的 JPEG 图片落盘路径
    model_path TEXT,                  -- 产生预测的模型路径（可选）
    created_at TEXT NOT NULL,
    used_for_retrain INTEGER DEFAULT 0  -- 是否已用于重训
);

CREATE TABLE models (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    version TEXT NOT NULL UNIQUE,     -- 模型版本号（v1、v2…）
    file_path TEXT NOT NULL,          -- 模型二进制文件路径
    created_at TEXT NOT NULL,
    note TEXT
);

CREATE TABLE devices (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id TEXT NOT NULL UNIQUE,
    first_seen TEXT NOT NULL,
    last_seen TEXT NOT NULL
);
```

设计要点：

- 图片以原始 JPEG 二进制落盘于 `data/inbox/{device_id}/` 目录，数据库仅保存路径索引，避免大字段拖慢数据库操作；
- `used_for_retrain` 标志位区分"尚未参与训练"的记录，为重训任务提供增量数据源；
- 设备表记录各边缘端首次/最近上报时间，便于设备管理。

### 3.3 接口实现

#### 3.3.1 批量上报推理数据（`POST /api/v1/sync_data`）

处理流程：

1. 鉴权：校验 `Authorization: Bearer <token>`，失败返回 401；
2. 请求体校验：`device_id` 必填；`records` 为非空列表；批量条数不得超过上限（默认 50，约 3 MB）；
3. 单条记录校验：时间戳须为合法 ISO-8601 格式；`label` 非空字符串；`confidence` 数值且位于 [0, 1]；`image_base64` 须为合法 Base64 且解码后非空、不超过体积上限（默认 10 MB）；任一项不合规则返回 400 并指明具体字段；
4. 数据落盘：Base64 解码为 JPEG 字节流，写入 `data/inbox/{device_id}/{timestamp}.jpg`（重名自动追加序号）；
5. 入库：向 `records` 表插入记录，更新设备最后活跃时间；
6. 触发重训：若开启自动重训（`AUTO_RETRAIN_ON_SYNC`，默认开启）且本批数据全部存储成功，则在后台线程调用重训扩展点（见 3.4）；
7. 返回 `{"code": 200, "message": "success", "synced_count": N}`。

#### 3.3.2 获取最新模型（`GET /api/v1/get_latest_model`）

处理流程：

1. 鉴权，失败返回 401；
2. 读取可选查询参数 `current_version`（边缘端当前模型版本）；
3. 查询模型仓库最新版本：
   - 无任何已发布模型，或 `current_version` 与最新版本一致 → 返回 `304 Not Modified`（无 Body）；
   - 存在更新版本 → 返回 `200 OK`，`Content-Type: application/octet-stream`，Body 为模型二进制（`.onnx`），响应头携带 `X-Model-Version: vN`。

#### 3.3.3 错误码映射

| 状态码 | 场景 | 边缘端处理 |
| :--- | :--- | :--- |
| 200 | 请求成功 | 正常处理 |
| 304 | 无新模型 | 忽略，继续使用当前模型 |
| 400 | 参数错误（Base64、时间戳、置信度、批量超限） | 检查本地序列化逻辑 |
| 401 / 403 | 鉴权失败 | 检查 Token 配置 |
| 404 | 路由不存在 | 检查服务端路由 |
| 500 | 服务端内部错误 | 触发重试机制 |

### 3.4 重训扩展点（Retrain Socket）设计

考虑到重训算法（如监督微调、强化学习 DQN 等）属于可独立迭代的研究内容，服务端将重训逻辑设计为**开放扩展点**，而非硬编码训练流程：

- 用户在 `retrain.py::run_retraining()` 中实现自有训练管线，服务端在数据同步完成后自动调用；
- 调度器使用线程锁保证同一时刻至多一个重训任务在后台运行，训练过程不阻塞 API 响应；
- 若 `run_retraining()` 尚未实现，服务端记录 WARNING 日志并继续正常提供 API 服务，不影响边缘端数据上报与模型下发；
- 扩展点向用户提供完整的数据与发布接口：`database.get_unused_records()`（拉取未参与训练的记录）、`database.mark_records_used()`（标记已训练）、`models_store.next_version()`（版本递增）、`models_store.publish_model()`（注册新模型并对外发布）。

该设计将"数据管理与版本发布"与"模型训练"解耦：服务端负责数据闭环的工程保障，训练算法由研究人员独立开发，二者通过清晰的函数接口协同，便于后续快速接入各类主动学习 / 强化学习算法。

## 4. 边缘端对接实现

边缘端（树莓派，主机名 rpi-g16，Raspberry Pi OS，AArch64）运行基于 Flask 的 Web 应用，主要模块包括：

- `onnx_inference.py`：基于 ONNX Runtime 的推理管理，采用**双缓冲热更新**机制——新模型加载失败时自动回退，保持当前可用模型不变；
- `data_collector.py`：本地 SQLite 数据采集，每 4 次推理且置信度 ≥ 0.5 的帧编码为 Base64 存入待同步队列；
- `api_client.py`：HTTP 客户端，携带 Bearer Token，对网络错误及可重试状态码（408/429/5xx）执行指数退避重试，对客户端错误（400/401/403/404）立即抛出；
- `sync_manager.py`：定时同步管理器，批量上报待同步记录，成功后标记 `is_synced`；
- `app.py`：集成上述模块，提供实时视频监控、推理结果展示、手动同步（`/api/sync_now`）与模型检查（`/api/check_model`）等 Web 接口。

边缘端通过环境变量 `SERVER_URL` 与 `SERVER_TOKEN` 配置服务端地址与鉴权凭据，无需修改代码即可切换服务端。

## 5. 端云联调测试过程与结果

联调在真实局域网环境进行：服务端运行于 PC（Windows，IP `192.168.1.5`，端口 8000，Waitress 生产服务器），边缘端运行于树莓派（IP `192.168.1.16`）。测试覆盖通信协议、鉴权、数据同步、模型下发与热更新等全链路环节。

### 5.1 边缘端 HTTP 客户端联调（5/5 通过）

在树莓派侧使用边缘端自有的 `ApiClient` 模块执行 5 项用例，全部通过：

| 编号 | 用例 | 期望结果 | 实测结果 |
| :--- | :--- | :--- | :--- |
| 1 | `sync_data` 上报 2 条记录 | 200，`synced_count=2` | 通过（`synced_count=2`） |
| 2 | `get_latest_model?current_version=v1` | 304，无新模型 | 通过（返回 None） |
| 3 | `get_latest_model`（版本落后） | 200 + 二进制 + `X-Model-Version` | 通过（下载并保存 `models/server_v1.onnx`） |
| 4 | 错误 Token 上报 | 401 鉴权失败 | 通过（抛出 `ApiAuthError`） |
| 5 | 非法 Base64 上报 | 400 参数错误 | 通过（服务端返回明确错误信息） |

### 5.2 数据同步闭环（边缘端 → 服务端）

1. 通过树莓派 `ApiClient` 上报 2 条记录，服务端返回 `synced_count=2`，随后在服务端数据库确认记录入库、图片成功落盘至 `data/inbox/pi-test-001/`；
2. 运行完整边缘端应用（`SERVER_URL=http://192.168.1.5:8000`，设备 ID 为 `pi-g16`）。在无摄像头接入的情况下，系统自动降级为合成帧继续运行，验证了系统的容错能力；
3. 向边缘端本地数据库写入 2 条待同步记录，调用边缘端 `/api/sync_now` 及后台同步线程（每 20 秒），共向服务端同步 10 条记录；
4. 服务端数据库记录总数增至 13 条，全部标记为"未参与训练"，服务端自动触发重训扩展点（日志记录 WARNING：扩展点尚未实现）。

### 5.3 模型下发与热更新闭环（服务端 → 边缘端）

1. **版本对比逻辑验证**：服务端发布模型 v1 后，边缘端携带 `current_version=v1` 请求返回 304；当边缘端版本落后时返回 200 与 `X-Model-Version` 头；
2. **热更新容错验证**：服务端发布伪造的 v2 模型（非合法 ONNX 文件），边缘端下载后于模型加载阶段检测到 protobuf 解析失败，自动回退并保持原模型继续推理，`last_error` 记录了失败原因——验证了双缓冲热更新机制对异常模型的容错能力；
3. **成功热更新验证**：服务端将边缘端自带的真实 ResNet-18 ONNX 模型（44 686 353 字节）注册为 v3，边缘端 `/api/check_model` 成功拉取并通过 ONNX Runtime 加载校验，`current_path` 切换为 `models/server_v3.onnx`，`last_error` 为空，模型版本记录为 v3——完整的"重训 → 发布 → 下发 → 热更新"闭环打通。

### 5.4 网络环境说明

- 局域网内 HTTP 通信正常（边缘端 → 服务端 200 响应）；
- 服务端所在 PC 的 Windows 防火墙默认拦截 ICMP（ping 不通），但不影响 HTTP 服务，实际部署中需在防火墙放行服务端口（8000）。

## 6. 测试中发现的问题与解决

| 问题 | 现象 | 分析与解决 |
| :--- | :--- | :--- |
| `send_file` 附加响应头失败 | 模型下发返回 500 | Flask 3.1 的 `send_file` 不支持 `headers` 关键字参数。改为先通过 `make_response(send_file(...))` 构造响应，再向响应对象设置 `X-Model-Version` 头，问题解决 |
| 伪造模型导致热更新报错 | 边缘端加载 v2 模型时 protobuf 解析失败 | 属于预期容错行为而非缺陷：边缘端双缓冲机制捕获异常并回退到原模型，验证了异常模型的防护逻辑；随后发布真实 ONNX 模型后热更新成功 |
| 防火墙 ICMP 不通 | ping 服务端无响应 | Windows 防火墙默认策略所致，HTTP 服务不受影响；部署时需开放对应端口入站规则 |

## 7. 结论与展望

### 7.1 结论

本阶段完成了服务端系统的重新设计与实现，并成功通过端云联调验证：

1. 服务端实现了接口规范定义的两个核心接口（数据上报、模型下发），支持 Bearer Token 鉴权、批量校验、SQLite 持久化存储与模型版本管理；
2. 重训扩展点设计将数据闭环与训练算法解耦，为后续主动学习 / 强化学习算法的接入提供了清晰接口；
3. 端云闭环在真实局域网环境下全链路打通：边缘端数据可稳定上报并落盘，服务端发布的新模型可被边缘端安全地热更新加载，异常模型可被自动隔离回退。

### 7.2 展望

后续工作方向包括：

1. 在 `retrain.py` 重训扩展点中接入基于 GhostNet/ResNet 的监督微调与基于 DQN 的强化学习微调管线，形成完整的"数据 → 重训 → 发布"自动化闭环；
2. 增加多设备并发上报的负载测试与断点续传机制；
3. 将接口迁移至 HTTPS（TLS 1.3）以保障传输安全，并引入设备级证书双向认证；
4. 探索 INT8 量化模型下发与差分传输，降低边缘端带宽消耗与加载延迟。
